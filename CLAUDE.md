# Fred Beans Mobile Service

## Overview
Internal Flask app for the mobile service team. Four top-level sections:
- **Account Management** — existing customer accounts and new leads (CRM)
- **Recall Checker** — Ford VIN recall lookups (one-time, scheduled, run log)
- **Used Car Tracker** — iframes an external Vercel app (`used-car-lot-recall-sweeper.vercel.app`) that sweeps used-car lot inventory for open recalls
- **Mobile Keys** — Key Database for tracking each key cut (vehicle, parts + costs, P&L). One row per key with computed totals on display.

Recall data is scraped via Selenium, results are written to Excel and emailed via Resend. Account/lead/schedule data lives in Supabase Postgres.

**Production URL:** http://dashboard.fredbeans-mobileservice.com/ (DigitalOcean droplet, nginx reverse-proxies port 80 → container on `127.0.0.1:5000`). Domain `fredbeans-mobileservice.com` is owned by the user; the `dashboard` A record points at the droplet. The old `recallchecker.fredbeans-mobileservice.com` hostname was retired on 2026-05-10 — DNS record was renamed (not duplicated), and the nginx `server_name` in `/etc/nginx/sites-available/recallchecker` was updated to match.

## Tech Stack
- **Backend:** Python / Flask (single-file app, no blueprints)
- **DB:** Supabase Postgres (via `supabase-py`)
- **Scraping:** Selenium (headless Chromium)
- **Excel:** openpyxl
- **Email:** Resend API
- **Scheduler:** APScheduler (cron triggers, single-process)
- **Hosting:** DigitalOcean (Docker, Gunicorn)
- **Templates:** Jinja2 HTML in `templates/` with inline CSS (no framework)

## Routes (high-level)
- `/` — home tile page (Account Management / Recall Checker)
- `/accounts` and `/accounts/new`, `/accounts/<id>/edit`, `/accounts/<id>/delete`
- `/cold-leads` — Lead Tracking (Xtime follow-up). Native spreadsheet-style page backed by the `cold_leads` Supabase table. Six market tabs (Doylestown / Exton / Langhorne / Newtown / Mechanicsburg / Washington); each tab renders existing DB rows newest-first (`list_cold_leads` orders by `created_at desc`). The "+ Add Row" button (above the table) inserts a fresh blank row at the **top** and focuses it; the new row auto-promotes to a DB row on first input (debounced 500ms POST to `/cold-leads/api/create`) — blank rows are never persisted. Saved rows update via `/cold-leads/api/update/<id>`. Rows with no `contact_date` (not yet called) get a subtle grey tint (`tr.no-contact`); the hot-lead green tint overrides it. A truncated Notes cell shows the full note in a hover popup (`showNoteTip`/`#noteTip`). Phone numbers auto-format to `(NNN-NNN-NNNN)` on blur. Name/phone blur fires a soft-duplicate check against all other `cold_leads` rows (server endpoint `/cold-leads/api/check-duplicate`) and surfaces matches in a centered modal (`showDupToast`) with a "Go to record" button per match that switches to the match's market tab (`goToRecord`) and flashes the existing row (`highlightRecord`, matched via `tr[data-id]`); dismiss via the × or backdrop click. Does not block save. Each market tab is split into two stacked, independently scrollable tables (`renderRows` partitions on `hot_lead` via the shared `buildRow`): a main non-hot table and a "Hot Prospects" table below it; toggling the Hot? checkbox re-renders to move the row between them. The Hot Prospects table has an extra "Appt Booked?" checkbox column (next to Hot?); a hot row tints yellow with no appointment and green once Appt Booked? is checked, both overriding the grey no-contact tint. Within the main (non-hot) table, `renderRows` floats uncalled rows (no `contact_date`, grey via `hasNoContact`) to the top via a stable sort, so still-to-call leads stay above already-contacted ones; the Pipeline Summary's grey-row count card is labeled "Uncalled Leads". A "⬆ Upload Appointments" button (next to + Add Row) drives the fleet-prospecting bulk import — see the `/cold-leads/api/parse-upload` + `import` routes below.
- `/recall-checker` — one-time VIN check form (posts to `/submit`). Accepts `?account_id=<id>` to prefill VINs and customer name from an account.
- `/recall/run-log` — recent ad-hoc jobs, persisted in the Supabase `one_time_runs` table (survives container restarts). The in-memory `jobs` dict in `app.py` is still used for live progress polling on `/status/<job_id>`. Clicking the VIN count opens a modal with the original VIN list + a Copy button so the rep can re-run it.
- `/schedules` and children — recurring recall checks
- `/notes` (GET/POST) — shared scratchpad page under Account Management. Auto-saves a couple seconds after typing stops via JSON POST; falls back to a normal form POST if JS is off. `beforeunload` fires `navigator.sendBeacon` to save on tab close.
- `/dashboard` — 302 redirect to `/recall/run-log` (back-compat)
- `/mobile-keys` — Key Database list (table of all rows, newest first). Row actions: Edit + Inventory only — Delete is reachable only from the edit form.
- `/mobile-keys/new`, `/mobile-keys/<id>/edit`, `/mobile-keys/<id>/delete` — CRUD endpoints
- `/mobile-keys/<id>/toggle-status` (POST) — flips the per-row `status_done` checkbox in the "Complete" column. Unchecked rows render with a light-grey row tint. The list's three checkbox columns run Ordered, Key Code, Complete (left to right).
- `/mobile-keys/<id>/toggle-ordered` (POST) — flips the per-row `ordered` checkbox in the leftmost "Ordered" column. Same checkbox style; does not tint the row.
- `/mobile-keys/<id>/key-code` (POST) — sets the per-row `key_code` checkbox state plus the actual `key_code_value` text. The "Key Code" column (between Ordered and Complete) is a checkbox-style button; clicking it opens a modal with a text box for the key code. "Save" stores the code and checks the row; "Uncheck" clears both. Does not tint the row.
- `/mobile-keys/<id>/notes` (POST) — sets/clears the per-row `notes` text. Driven by the leftmost "Notes" column on both list pages: every row has a notepad button (solid blue when a note exists, faint grey when not), hover reads the note, click opens a modal to edit it. Blank/whitespace saves as NULL. A `return_to=inventory` form field sends the redirect back to the Inventory page instead of the Key Database.
- `/mobile-keys/<id>/move-to-inventory`, `/mobile-keys/<id>/restore-from-inventory` — toggle the inventory flag on a key
- `/mobile-keys/inventory` — Inventory list (parts that were ordered but the customer no longer needs them; shows Date/Year/Make/Model + part numbers and costs only)
- `/mobile-keys/contacts` — Key Code Contacts page. A small inline-edit reference table (Store / Name / Email / Notes) of who to reach out to at each store for a key code. Spreadsheet-style: type directly in cells, rows auto-save (debounced 600ms), "+ Add Contact" appends a blank row, the × deletes. The Store column header is click-to-sort (alpha, toggles asc/desc; blank-store rows sink to the bottom). Backed by the `key_code_contacts` table.
- `/mobile-keys/contacts/api/create` / `update/<id>` / `delete/<id>` (POST, JSON) — JSON API powering the Key Code Contacts table.
- `/cold-leads/api/list?market=<m>` (GET) / `create` / `update/<id>` / `delete/<id>` / `check-duplicate` (POST, JSON) — JSON API powering the cold-leads spreadsheet. Save/update is debounced client-side (500ms); blanks-only ghost rows are not persisted.
- `/cold-leads/api/parse-upload` (POST, multipart) / `import` (POST, JSON) — power the "⬆ Upload Appointments" button on the Lead Tracking page (fleet prospecting). `parse-upload` takes a DMS appointments `.xlsx` (`excel_file`), runs `appt_importer.parse_appointments` to classify commercial-business rows, drops any that already exist as cold leads (one-pass in-memory dedup against `db.list_cold_leads()` on lowercased name / 10-digit phone), and returns `{candidates, skipped_existing, skipped_people, skipped_dealers, unmatched_market}` for a client-side preview modal — nothing is inserted yet. The modal lists candidates (per-row checkbox, pre-checked, plus a × to remove; select all/none) and only the rows still checked on confirm are POSTed to `import`, which forces `source='Xtime'`, validates each via `_clean_cold_lead_payload`, and inserts via `db.create_cold_lead`. Classification (`appt_importer`): the DMS exports people as `LASTNAME, FIRSTNAME`, so the **comma is the primary signal** and the keyword set is conditioned on it — no-comma names use a broad business-keyword list aggressively; comma names are businesses only if a strong entity suffix (`INC`/`LLC`/`CORP`/…) sits adjacent to the comma (so `GLASS, ELIZABETH` stays a person but `CORP, APS B SAFE` / `MARQUIS CONSTRUCTION SERVICES, INC` are caught). Car dealerships (own `FRED BEANS …` + competitors, brand tells like `CHEVROLET`/`MOTORS`) are always excluded via `DEALER_EXCLUDES` — this is fleet prospecting. Fixed columns in the export: **A** = store (mapped to a market tab by substring), **C** = lead date (`MM/DD/YYYY`→ISO), **L** = customer full name, **M** = phone (formatted to `(NNN-NNN-NNNN)`). Rows whose store doesn't map to a `COLD_LEAD_MARKETS` tab are skipped.
- `/test-supabase`, `/test-chrome` — health checks

## Supabase tables
- `one_time_runs` — one row per ad-hoc `/submit` recall check. Columns: `job_id` (12-char hex from app.py), `started_at`, `finished_at`, `status` (queued/starting/running/complete/error), `vin_count`, `vins` (text[] — the original list, used by the run-log modal for copy/re-run), `recalls_found`, `customer_name`, `output_file`, `email`, `email_sent`, `error`. Rows are INSERTed in `submit()` at queue time and UPDATEd by the worker on status transitions. Best-effort writes — Supabase failures don't break the in-memory job. Note: a container killed mid-job leaves the row in `status='running'` (no startup sweep).
- `schedules` — recurring recall checks. Optional `account_id` FK to `accounts`. `cadence` is one of `daily`/`monthly`/`quarterly` (the legacy `weekly` was dropped in the 2026-05-11 migration). `anchor_at` (nullable timestamptz) is the first-fire timestamp for monthly/quarterly rows; the scheduler builds an `IntervalTrigger` of 30 or 90 days starting at that anchor. Null `anchor_at` falls back to the legacy cron behavior (1st of the month, or 1st of Jan/Apr/Jul/Oct).
- `schedule_runs` — per-execution log (started_at, finished_at, recalls_found, email_sent, error)
- `notepad` — shared scratchpad behind `/notes`. Single-row table — a CHECK constraint pins `id = 1`, so `db.get_notepad()` / `db.save_notepad()` always read/write that one row. No history kept.
- `accounts` — master record for an existing customer (company, market, account_rep, fleet manager contact, service_type, VINs, notes). Supports an optional second fleet manager (`fleet_manager_2`, `fleet_manager_2_email`, `fleet_manager_2_phone`). Also stores origin context the same way leads do: `lead_source` ∈ `Sales`/`Service`/`Parts`/`Visual`/`Other` (nullable), `lead_source_other` (only when source is Other), `source_contact` (only for Sales/Service/Parts). The lead→account convert flow carries these over from the source lead. Check-in column: `last_checked_in_at` (timestamptz) + `check_in_note` (nullable text) — both editable from the accounts table cell. The cell opens a modal that lets the rep either save just a note (no date change, via `/accounts/<id>/check-in-note`) or check in (bump date + save note, via `/accounts/<id>/check-in`). When the cell is already green, only "Save note" is offered — re-check-in waits for the 25-day auto-flip (`ACCOUNT_CHECK_IN_DAYS = 25`). Note is never required and is shown in the cell's hover tooltip.
- `account_leads` — prospects. **The Warm Leads UI was removed; this table is retained for its data and for the dup-check, but is no longer created/edited through the app.** Columns: (company, market, account_rep, phone, notes, optional `fleet_manager` / `fleet_manager_email` — collected for both lead types). Split into two workflows via `lead_type` (`cold` or `warm`); warm prospects additionally use `last_contacted_at`. `interest_level` (R/Y/G, default Y) still exists on the row but the lead form no longer collects it — new/edited leads fall back to `INTEREST_LEVEL_DEFAULT`. `lead_source` ∈ `Sales`/`Service`/`Parts`/`Visual`/`Other`; `source_contact` (free text) is only meaningful for Sales/Service/Parts and is cleared otherwise. Contact attempts are tracked on the row via `last_attempt_at` / `last_attempt_outcome` (`made_contact` or `left_voicemail`) / `last_attempt_note` — only the latest attempt is kept (no history table). `closed_at` + `closed_reason` soft-close a lead so it drops off the active list (mirrors how `converted_at` hides converted leads); `list_leads(include_converted=False)` filters out both converted and closed rows. `converted_at` + `converted_account_id` are set when a lead is converted.
- `cold_leads` — one row per Xtime follow-up prospect. Columns: `market` (one of the 6 stores in `COLD_LEAD_MARKETS`), `name`, `phone` (stored in display format `(NNN-NNN-NNNN)` — formatted client-side on blur), `source` (`Sales`/`Service`/`Parts`/`Xtime`/`Other`, nullable), `lead_date` (when the lead came in), `contact_date` (when we reached them) — both stored ISO but shown/edited as compact `M/D/YY` text cells (`formatDateDisplay`/`parseDateInput`, parsed on blur), `notes`, `hot_lead` (boolean — moves the row into the Hot Prospects table), `appt_booked` (boolean, default false; added in the 2026-06-17 migration — surfaced as a second checkbox column next to Hot? in the Hot Prospects table only). Hot-row tint: yellow when hot but no appointment booked, green once `appt_booked` is checked (`tr.hot-lead` vs `tr.hot-lead.appt-booked`). All fields are nullable except market — the page renders ghost rows that aren't persisted until the user types something in. The duplicate check (`find_cold_lead_duplicates`) matches name (case-insensitive) and phone (digits-only, requires ≥10 digits) across all markets.
- `mobile_keys` — one row per key cut. Columns: `cut_date`, `end_user` (`Internal`/`Customer`), `customer_name` (Internal = one of `KEY_INTERNAL_CUSTOMERS` = `FB Chevrolet, FB CDJR, FB Hyundai, FB Lincoln, FB Ford, FB Subaru, FB Toyota, Bid Lot` — the seven Fred Beans dealerships are prefixed `FB `; `Bid Lot` is not a dealership and stays bare; Customer = free text), `internal_contact` (nullable text — optional person attached to an **Internal** key, for when the car was already sold and the key gets cut at the buyer's house; the store is still billed. Surfaced as an optional "Contact Name" input inside the Internal block on the add/edit form, so the existing `syncEndUser()` show/hide handles it. Server-side it's forced to NULL whenever billing is Customer, so flipping the radio drops a stale value. Added in the 2026-08-10 migration, no backfill), `ro_number`, `vin`, `year`, `make` (from `KEY_MAKES` ~21 brands), `model`, `key_type` (`Fob`/`Turnkey`/`Flip Key`), `key_fob_part_number`/`key_fob_cost`, `key_blank_part_number`/`key_blank_cost`, `programming_cost` (form field is a dropdown — `$60` / `$100` / `Other` (free-text). Default follows the **Billing Information** radio: `$60` when Internal (`KEY_PROGRAMMING_COST_INTERNAL`), `$100` when Customer (`KEY_PROGRAMMING_COST_CUSTOMER`); changing the radio re-applies the default, but the user can override. Empty submit still falls back to `KEY_PROGRAMMING_COST_DEFAULT` = $60), `offset_eligible`, `moved_to_inventory_at` (nullable timestamptz — non-NULL means the part was moved to the Inventory page because the customer no longer needed it; these rows are hidden from the main Key Database list and only appear on the Inventory page), `status_done` (boolean, default false — toggled by the "Complete" checkbox; pending rows render with a light-grey tint. The 2026-05-12 migration backfilled all pre-existing rows to true), `ordered` (boolean, default false — toggled by the leftmost "Ordered" checkbox; the 2026-05-14 migration backfilled existing rows to true), `key_code` (boolean, default false) + `key_code_value` (nullable text — the actual key code) — surfaced by the "Key Code" checkbox between Ordered and Complete; clicking it opens a modal to enter the code. The 2026-05-19 migration does NOT backfill, so existing rows start unchecked. `notes` (nullable text) — free-text scratchpad per key. Editable two ways, both writing this same column: the textarea at the bottom of the add/edit form, and the **Notes column** (leftmost on both the Key Database and Inventory lists — see `/mobile-keys/<id>/notes`). The old notepad icon beside the customer name is gone; `accounts.notes` still uses that older inline pattern. Derived columns (Total Parts, Total Cost, plus `customer_display` = `customer_name` joined with `internal_contact` as `FB Chevrolet - Mark Macy`, falling back to the bare `customer_name`) are computed in `app.py` `_compute_key_totals()` at render time, not stored — both the Key Database list and the Inventory list route rows through that helper and render `customer_display`. **Total Cost is a billed total:** `parts_total * (1 + markup) + programming_cost`, where the parts markup depends on the billing (`end_user`): Internal 10% (`KEY_MARKUP_INTERNAL`), Customer 35% (`KEY_MARKUP_CUSTOMER`). The Total $ column header has an (i) info tooltip explaining this. (The old Parts Discount column was removed — both the list column and the `discount_needed` computation.) The form's "End User" label was renamed to "Billing Information" (the underlying `end_user` column/values are unchanged — still `Internal`/`Customer`).
- `key_code_contacts` — backs the Key Code Contacts page under Mobile Keys. One row per contact, columns `store` / `name` / `email` / `notes` — all free text and nullable. Rows are typed in inline (spreadsheet-style) and auto-saved via the `/mobile-keys/contacts/api/*` JSON endpoints. No dropdowns, no validation; purely a reference list.

`MARKETS` (and the `location`/`market` check constraints) use: Boyertown, Doylestown, Exton, Langhorne, Newtown, Washington, West Chester, Mechanicsburg, Company-Wide. The legacy value `GroupWide` was renamed to `Company-Wide` in the 2026-05-07 migration.

## Environment Variables
- `SUPABASE_URL`, `SUPABASE_KEY` — required; the app fails fast on first DB call without them.
- `RESEND_API_KEY` — API key for Resend email service
- `RESEND_FROM_EMAIL` — From address for email (default: `fordrecalls@voxapp.co`)
- `USE_GH_ACTIONS_FOR_RECALLS` — set to `1` on hosts whose egress IP is blocked
  by Ford's Akamai (DigitalOcean prod, Fly, etc.). Routes recall checks through
  the `recall_check_on_demand` workflow in this same repo (which runs on
  GitHub-hosted Azure IPs that Akamai allows). Leave unset for local dev —
  residential IPs aren't blocked.
- `GH_ACTIONS_TOKEN` — GitHub PAT (`actions:write` + `actions:read` on
  `CGilbert23/FordRecallCheckScript`); required when the flag above is set.
- `GH_ACTIONS_REPO` — target repo, e.g. `CGilbert23/FordRecallCheckScript`.
- `GH_ACTIONS_WORKFLOW` — workflow filename, default `recall_check_on_demand.yml`.
- `GH_ACTIONS_REF` — branch to dispatch against, default `main`.

## Notes
- One-time recall jobs run in background threads and results are stored in `outputs/`. Live job state (progress %, in-flight status, output_file) is in-memory only — restart wipes the `jobs` dict and the `/job/<id>` and `/status/<id>` endpoints will show "Job not found" for old IDs. The historical *run log* itself is persisted to the Supabase `one_time_runs` table and survives restarts (scheduled runs continue to log to `schedule_runs` separately).
- `/submit` is rate-limited to 200 VINs per rolling 6 hours (`RATE_LIMIT_MAX_VINS`/`RATE_LIMIT_WINDOW` in `app.py`). The check is "is the window already full?" — submissions aren't capped by size, so a 400-VIN job goes through if the window had room, then locks out further submits until enough of those 400 ages past 6 hours. State is in-memory only (lost on restart) and scheduled runs are exempt.
- Single Gunicorn worker (see `gunicorn.conf.py`) keeps APScheduler to one instance — don't bump worker count without revisiting that.
- Selenium requires a compatible Chrome/Chromium + ChromeDriver setup (handled in the Dockerfile).
- `recall_checker.py` clears cookies/storage before each VIN and gates parsing on the searched VIN actually appearing on the results page. If it doesn't (stale/stuck page), `check_ford_recall` returns `hasRecall=None`; `process_recalls` then restarts the browser and re-checks that same VIN (up to 2 retries) before counting it as an error — without the retry a stale-page VIN was silently dropped from the output Excel.
- The mobileservice@fredbeans.com address is auto-CC'd on every scheduled email; no need to add it to recipient lists.
- The account create/edit form runs a soft-duplicate check (`db.find_duplicate_matches`) against existing accounts + active leads on company name (case-insensitive exact), email (case-insensitive exact, sentinel `--` ignored), and phone (digits-only exact). On a match the form re-renders with a yellow warning banner; the user must resubmit with the hidden `confirm_duplicate=1` flag (set automatically by the "Save anyway" button) to bypass. The banner only links to matched *accounts* now that the Warm Leads page is gone (lead matches show without a link).
- The Warm Leads page and all `/leads*` routes (`leads_list`, `lead_new`, `lead_edit`, `lead_delete`, `lead_attempt`, `lead_last_contacted`, `lead_convert`) plus the `leads.html`/`lead_form.html` templates and the `_read_lead_form`/`_lead_payload`/`_lead_form_context` helpers were removed (no longer used by the team). The `account_leads` table is retained (data preserved) but is no longer surfaced in the UI. `db.py` lead functions (`list_leads`, `create_lead`, `get_lead`, `update_lead`, `delete_lead`, `record_lead_attempt`, `convert_lead_to_account`, `promote_lead_to_warm`, `LEAD_*` constants) still exist; `convert_lead_to_account` and `find_duplicate_matches` remain in use by the accounts flow, the rest are now dead code.
- Schedule firing: daily uses a cron trigger at 6am ET; monthly/quarterly use `IntervalTrigger` (30/90 days) starting at `anchor_at`. On create, `_compute_anchor_at()` sets the anchor to today + 30 or 90 days at 6am ET. On edit, the anchor is only reset when the cadence itself changes — otherwise the existing anchor is preserved.
- The `/schedules/<id>/run` POST route (`schedule_run_now`) still exists, but the "Run Now" button on the schedules list was removed in the 2026-05-11 commit — the endpoint is no longer reachable from the UI.
